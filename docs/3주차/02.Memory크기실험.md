# 3주차 - Memory 크기 실험 (단계 2)

> 아직 이 파일은 실험 계획 상태다. 1단계에서 Memory 통로가 열린 것을 확인했으니, 이제 크기 제한이 작거나 너무 클 때 어떤 식으로 망가지는지를 숫자와 실패 출력으로 잡는다.

## 실험 질문

`MessageWindowChatMemory`의 `MAX_MESSAGES`는 단순한 설정값이 아니다. 너무 작으면 지시 대명사를 풀 근거가 사라지고, 너무 크면 입력 토큰과 응답 시간이 계속 늘어난다.

이번 단계의 질문은 세 가지다.

- `MAX_MESSAGES = 20`에서 10턴 상담이 어느 정도 유지되는가.
- `MAX_MESSAGES = 2`에서 어떤 턴부터 "그거", "아까 그 주문"이 깨지는가.
- 사실상 무제한에 가까운 값에서 입력 토큰이 얼마나 빠르게 늘어나는가.

## 고정할 조건

- 모델: Ollama `qwen2.5`
- temperature: `0.3`
- 엔드포인트: `/api/v1/assistant`
- 세션 ID: 실험마다 새 `X-Session-Id`
- 측정 로그: `PerformanceLoggingAdvisor`의 `promptTokens`, `completionTokens`, `elapsedMs`
- 판단 로그: `[Tool] getDeliveryStatus`, `[Tool] getOrderDetail`, `[Tool] cancelOrder`

## 실행할 10턴 시나리오

```text
1. 2024-1234 배달 상황 알려주세요
2. 그거 몇 분 남았어요?
3. 2024-1235 주문도 있는데 메뉴 뭐였죠?
4. 아 그 버거 세트
5. 2024-1234 취소 가능해요?
6. 그럼 1235는 취소되죠?
7. 그거 취소해주세요
8. 아까 1234는 언제 도착해요?
9. 그 주문 라이더 위치 다시 확인
10. 요약해 주세요 지금까지 제가 뭘 물어봤는지
```

## 정량 비교

| 실험 | MAX_MESSAGES | 10턴 평균 입력 토큰 | 10턴 평균 출력 토큰 | 10턴 평균 응답 시간 | 지시 대명사 해결 성공 |
| --- | ---: | ---: | ---: | ---: | ---: |
| A | 20 | 2133.5 | 68.5 | 2711.4ms | 6/10 |
| B | 2 | 1853.5 | 68.9 | 2849.8ms | 2/10 |
| C | 100000 | 2126.8 | 68.5 | 2706.4ms | 8/10 |

raw는 `실측-raw/단계2-memory-window-10턴.md`에 남겼다. 10턴만 놓고 보면 `20`과 `100000`은 큰 차이가 없었다. 이유는 단순하다. 10턴이면 USER/ASSISTANT 합산 20개 메시지라, `MAX_MESSAGES=20`도 아직 잘라내지 않는다. 무제한의 비용 위험은 20턴, 30턴으로 길어질 때 더 분명해질 것이다.

## MAX_MESSAGES = 2의 실패

`MAX_MESSAGES=2`는 마지막 USER/ASSISTANT 한 쌍만 남는다. 이 조건에서는 초반 두세 턴 뒤부터 맥락이 빠르게 무너졌다.

- 6턴 `"그럼 1235는 취소되죠?"`에서 `1235`를 `2024-1235`로 복원하지 못했다.
- 7턴 `"그거 취소해주세요"`도 직전 주문을 제대로 취소하지 못하고 주문번호를 찾지 못했다고 답했다.
- 10턴 요약은 전체 10턴이 아니라 직전 라이더 위치 질문만 요약했다.

최종 Memory가 이 사실을 그대로 보여준다.

```json
[
  {"type":"user","text":"요약해 주세요 지금까지 제가 뭘 물어봤는지"},
  {"type":"assistant","text":"당신은 다음과 같은 내용을 확인하셨습니다:\n1. 그 주문의 라이더 위치를 다시 확인했습니다.\n\n만약 다른 정보가 필요하시면 알려주세요."}
]
```

이건 "LLM이 요약을 못했다"보다 먼저, 요약할 과거 메시지가 Memory에 없었다는 쪽에 가깝다.

## 20과 100000의 차이가 작았던 이유

처음엔 `100000`에서 입력 토큰이 훨씬 커질 거라고 예상했다. 그런데 10턴에서는 평균 입력 토큰이 `20`과 거의 같았다.

```text
20:     prompt 평균 2133.5
100000: prompt 평균 2126.8
```

이 결과는 설정이 효과가 없다는 뜻이 아니다. 10턴은 정확히 20개 메시지라서 `MAX_MESSAGES=20`의 절단선에 걸리지 않는다. 무제한의 위험을 보려면 10턴이 아니라 30턴 이상으로 밀어야 한다. 이번 단계에서는 `2`가 왜 파괴적인지까지는 확인했고, `무제한이 선형 증가한다`는 주장은 아직 10턴 데이터만으로는 약하다.

## 다음 단계로 넘기는 것

JDBC 저장소 비교에서는 Memory 크기보다 저장소 수명과 인스턴스 경계를 본다. 이번 단계에서 확인한 것은 `MessageWindowChatMemory` 정책이 저장소 위에서 메시지 개수를 실제로 자른다는 점이다. 저장소를 JDBC로 바꿔도 이 정책 레이어는 그대로 남아야 한다.
