# 3주차 - InMemory와 JDBC 저장소 비교 (단계 3)

> 이 단계는 아직 구현 전이다. 여기서 보고 싶은 건 "JDBC로 바꿀 수 있다"가 아니라, 어떤 운영 조건에서 InMemory가 더 이상 답이 아닌지를 재시작과 세션 유지 실험으로 확인하는 것이다.

## 지금 상태

1단계 구현은 기본 profile에서 `InMemoryChatMemoryRepository`를 쓴다.

```java
@Profile("!jdbc")
ChatMemoryRepository chatMemoryRepository() {
    return new InMemoryChatMemoryRepository();
}
```

`@Profile("!jdbc")`를 미리 둔 이유는 JDBC profile에서 Spring AI 자동 구성이 `JdbcChatMemoryRepository`를 만들 수 있게 길을 열어두기 위해서다. 아직 의존성과 `application-jdbc.yml`은 붙이지 않았다.

## 구현할 것

`build.gradle`에 JDBC memory repository와 H2를 추가한다.

```gradle
implementation 'org.springframework.ai:spring-ai-starter-model-chat-memory-repository-jdbc'
runtimeOnly 'com.h2database:h2'
```

그 다음 `jdbc` profile로 실행한다.

```bash
./gradlew bootRun --args='--spring.profiles.active=jdbc'
```

## 비교할 조건

| 저장소 설정 | 재시작 후 Memory 유지? | 확인 방법 | 비고 |
| --- | --- | --- | --- |
| InMemory |  | 같은 세션 ID로 "그거" 재질문 | JVM 종료 시 소실 예상 |
| `jdbc:h2:mem:...` |  | 앱 재시작 뒤 같은 세션 조회 | DB도 메모리라 소실 예상 |
| `jdbc:h2:file:...` |  | 앱 재시작 뒤 같은 세션 조회 | 파일 기반 유지 예상 |

## 봐야 할 운영 판단

InMemory로 충분한 조건은 꽤 좁다.

- 단일 인스턴스다.
- 세션이 짧고, 서버 재시작 후 이어질 필요가 없다.
- 상담 이력을 감사나 CS 조회용으로 보관하지 않는다.

JDBC가 필요한 조건은 반대다.

- 로드밸런서 뒤 멀티 인스턴스다.
- 앱을 껐다 켜도 대화가 이어져야 한다.
- 상담 이력을 일정 기간 보관해야 한다.
