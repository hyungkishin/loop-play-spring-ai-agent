# Round 6 — 리뷰하는 자리와 리뷰받는 자리에서 다시 본 코드

5주차까지 AI 코드 리뷰는 "AI가 짠 예시 코드를 내가 본다"는 한 방향이었습니다.
6주차 목표는 양쪽이었어요. 내 코드를 남의 PR처럼 읽는 자리, 그리고 내가 올린 PR에 리뷰어가 뭘 물을지 먼저 서 보는 자리.

기준은 "프로덕션에 이대로 나가면 무슨 일이 생기나"로 잡았습니다.
가능하면 지적마다 이번 라운드에서 실제로 본 로그나 raw를 붙였고, 근거가 코드 읽기뿐인 건 그렇다고 적었습니다.

## 리뷰하는 자리 — 내 코드를 남의 PR처럼

### 이번에 고친 것

**RAG 저장소 하나가 죽으면 에이전트 전체가 죽는다.**
PgVector를 멈추자 RAG와 상관없는 주문 조회까지 30초 뒤 Fallback으로 떨어졌습니다. (`실측-raw/gemma4-장애주입.md`)
`QuestionAnswerAdvisor`가 검색 예외를 그대로 던지고, Hikari 기본 대기가 30초라서였어요.
`FailSoftVectorStore`와 `hikari.connection-timeout: 2000`으로 고쳤고, 같은 장애에서 주문 조회가 정상 응답하는 걸 다시 확인했습니다.

**토큰 메트릭이 두 배로 집계된다.**
같은 카운터 이름에 prompt / completion / total을 다 올려서, 태그 없이 보면 실제의 2배였습니다(65848 vs `type:total` 32924).
대시보드에서 `sum(baedal_agent_tokens_total)`을 그리면 그대로 틀린 그래프가 나오는 버그라, total 기록을 뺐습니다.

**지시어 규칙이 Memory와 충돌한다.**
"주문번호가 발화에 없다면 되묻는다"는 문장 때문에 gemma4가 Memory에 있는 주문번호를 다시 물었습니다.
프롬프트를 고치고 E2E 3턴이 Tool 호출로 바뀌는 걸 봤지만, `AssistantPromptTest`는 문장이 들어 있는지만 확인합니다. 모델 행동을 보장하는 테스트는 아닙니다.

### 남겨 둔 것 — 프로덕션이면 막아야 할 순서대로

**실험용 엔드포인트가 Guardrail 우회 경로다.**
`/api/v1/chat`과 `/api/v1/chat/stream`은 1주차 실험용이라 system prompt도, Input/Output Guardrail도, Handoff도 없습니다.
4주차 재실행에서 `/api/v1/chat`에 정책 질문을 넣었을 때 아무 제약 없이 1,000~2,000 토큰짜리 일반론을 돌려준 게 그 증거예요. (`docs/4주차/실측-raw/단계5-RAG유무비교-gemma4.md`)
같은 앱에 떠 있는 한, 공격자는 `/api/v1/assistant` 대신 이쪽을 두드리면 됩니다. 프로덕션이면 프로파일로 빼거나 지워야 합니다.

**Rate Limit은 `X-Forwarded-For`를 그대로 믿는다.**
`clientIp()`는 요청 헤더의 첫 값을 그대로 키로 씁니다. 헤더는 클라이언트가 마음대로 넣을 수 있어서, 요청마다 값을 바꾸면 카운터가 매번 새로 시작합니다. (코드 읽기로 확인)
이번 반복 실험 스크립트도 실험 간 간섭을 피하려고 요청마다 `X-Forwarded-For: 198.51.100.{k}`를 바꿔 보냈는데, 제가 쓴 그 편의 기능이 그대로 우회 방법이라는 걸 raw를 정리하다 알아챘어요.
다만 이 실험은 요청 하나가 10초 넘게 걸려 분당 5건 남짓이라, 우회가 아니었어도 제한에 닿지 않았습니다. 우회를 실측한 건 아닙니다.
신뢰할 수 있는 프록시 뒤에서만 이 헤더를 읽고, 아니면 `remoteAddr`를 써야 합니다.
IP별 deque가 청소되지 않는 문제는 Round 6 문서에 이미 적었습니다.

**기본 프로파일이 평문 PII를 로그에 남긴다.**
`application.yml`의 기본 로그 레벨이 `com.baedal: DEBUG`라서, `OutputGuardrailAdvisor`의 원본↔최종 대조 로그가 항상 켜져 있습니다.
이번 raw에도 `원본='네, 고객님의 연락처는 010-9876-5432로 확인되었습니다.'`가 그대로 남았어요.
마스킹을 하는 바로 그 컴포넌트가 마스킹 전 값을 로그에 흘리는 셈이라, 운영 프로파일에서는 INFO로 올려야 합니다.
학습 저장소에서는 이 로그가 관찰 도구라 기본값을 바꾸지 않았습니다.

**LLM 호출에 타임아웃이 없다.**
gemma4 한 턴이 6~21초였습니다. Ollama가 살아 있는데 느려지면 요청 스레드가 그만큼 묶이고, 지금 구조에서는 끊을 방법이 없습니다.
이번 장애 주입은 "연결 거부"만 재현했고 "느려짐"은 재현하지 않았습니다.

**`FailSoftVectorStore`는 모든 `RuntimeException`을 삼킨다.** (이번에 제가 넣은 코드)
연결 실패뿐 아니라 쿼리 버그도 "Context 없음"으로 보일 수 있습니다.
`baedal.agent.rag.failure`에 알람을 걸지 않으면 조용한 품질 저하가 됩니다.

**`SupportController`에는 메트릭이 없다.**
`AssistantController`는 `request` / `handoff` / `fallback`을 세는데, 같은 체인을 쓰는 `SupportController`는 하나도 안 셉니다. (코드 읽기로만 확인)
`/api/v1/support`로 들어온 Fallback은 대시보드에 안 잡힙니다.

**Tool 로그의 주문번호 마스킹이 디버깅을 막는다.**
2주차에 `2024-***`로 가리기로 했는데, E2E 7턴에서 모델이 어느 주문을 취소하려 했는지 로그만으로는 알 수 없었습니다.
응답 본문과 outcome 태그로 역산했어요. 주문번호가 이 도메인에서 개인정보인지부터 다시 따져 봐야 할 것 같습니다. 해시나 끝자리 일부 노출 같은 중간안도 있습니다.

**`llmLatency`에 histogram이 없다.** Round 6 문서의 대시보드 표에 적은 그대로라 여기서는 생략합니다.

## 리뷰받는 자리 — 이 PR을 올리면 무엇을 물을까

이번 변경을 PR 하나로 올린다고 치고, 리뷰어라면 뭘 물을지 먼저 적어 봤습니다.

**"모델 교체 PR에 왜 RAG, 메트릭, 프롬프트 수정이 섞여 있나요?"**
맞는 지적입니다. 모델 교체가 드러낸 문제를 같은 흐름에서 고치다 보니 섞였어요.
최소한 커밋은 모델 교체 / 턴 추적 / 프롬프트·threshold / fail-soft / 메트릭 버그로 나눠, 되돌릴 때 하나씩 되돌릴 수 있게 하는 게 맞습니다.

**"threshold 0.42의 근거가 20문장이면 부족하지 않나요?"**
부족합니다. 도메인 밖 최고점 0.389와 놓친 질문 최저점 0.426 사이의 좁은 틈에 그은 선이에요.
대신 근거를 코드 주석과 raw에 남겼고, 문서가 늘면 `scripts/scores.py`로 다시 재야 한다고 적었습니다. 이 PR이 주장하는 건 "0.5보다 낫다"까지이고 "0.42가 맞다"는 아닙니다.
threshold를 내리면서 무관한 환불 문서가 Context에 붙는 대가도 봤습니다.
실제로 그 뒤 임베딩을 `embeddinggemma`로 바꾸자 이 숫자는 통째로 의미를 잃었고, 다시 재서 0.5로 되돌렸습니다(`03`). 리뷰어가 "임베딩 모델이 바뀌면요?"까지 물었다면 할 말이 없었을 거예요.

**"FailSoft가 문제를 숨기지 않나요?"**
숨길 수 있습니다. 그래서 WARN 로그와 `rag.failure` 메트릭을 같이 남기게 했고, 적재 경로(`add`)는 감싸지 않았습니다.
알람 규칙까지는 이 PR에 없습니다.

**"TurnTraceAdvisor를 운영에도 두나요?"**
턴마다 INFO 한 줄이고 `conversationId`와 문서 id, 점수만 남깁니다. 사용자 발화나 응답 본문은 안 찍어요.
다만 `conversationId`가 곧 `X-Session-Id`라서, 세션 id가 식별자로 취급되는 환경이면 해시로 바꿔야 합니다.

**"프롬프트 수정이 다른 턴을 망가뜨리지 않았다는 건 어떻게 아나요?"**
수정 전 14턴과 수정 후 15턴을 같은 입력으로 돌려 비교한 것 말고는 없습니다. 각 한 번씩이라 확률적 차이와 수정 효과를 완전히 가를 수 없어요.
7턴은 수정 후에도 틀렸다는 것까지 PR 설명에 적어야 한다고 생각합니다.

## 정리하며

리뷰하는 자리에서 찾은 것 중 절반은 이번 라운드의 실험 도구가 드러낸 것이었습니다.
`X-Forwarded-For` 문제는 반복 실험 스크립트의 헤더를 보다가, PII 로그는 raw를 옮기면서, 주문번호 마스킹의 불편함은 7턴을 역산하면서 봤어요.
코드를 읽어서 찾은 것보다 코드를 써 보면서 걸린 게 더 많았다는 게 이번 리뷰의 솔직한 성적표입니다.

리뷰받는 자리에서는 "무엇을 고쳤나"보다 "무엇을 주장하지 않는가"를 적는 데 시간이 더 들었습니다.
threshold도, 프롬프트도, 한 번 돌린 E2E도 전부 "이 조건에서는 나아졌다"까지만 말할 수 있어서요.
