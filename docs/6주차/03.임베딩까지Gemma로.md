# Round 6 — 임베딩까지 Gemma로 바꾸고 다시 잰 것

`01` 문서에서 채팅 모델만 gemma4로 바꾸고 임베딩(`qwen3-embedding:0.6b`)은 그대로 뒀습니다. 비교 변수를 하나로 묶고 싶어서였어요.
그 뒤 모델을 전부 Gemma 계열로 맞추기로 해서, 임베딩을 `embeddinggemma`로 바꾸고 RAG에 걸린 숫자를 다시 쟀습니다.

raw는 `실측-raw/embeddinggemma-재측정.md` 한 파일에 모았습니다. 점수 분포, 키워드 대 임베딩, E2E 15턴, 마스킹 되읽기, 4주차 RAG 쪽, 5주차 반복이 순서대로 들어 있어요.

## 바꾼 것

`ollama show embeddinggemma` 기준 307.58M, BF16, 768차원입니다. qwen 쪽은 1024차원이었어요.

차원이 다르면 같은 테이블에 넣을 수 없습니다. PgVector의 `initialize-schema: true`는 테이블이 없을 때만 만들기 때문에, 기존 `vector_store`(vector(1024))를 직접 `DROP TABLE`하고 앱을 다시 띄워 768차원으로 7건을 새로 적재했습니다.
`application.yml`에서는 `embedding.model`과 `pgvector.dimensions` 두 줄을 바꿨습니다.

운영이었다면 이 한 줄짜리 설정 변경이 "전체 재색인"이라는 게 제일 먼저 걸렸을 것 같습니다. 채팅 모델은 설정 한 줄로 끝났는데, 임베딩 모델은 저장된 데이터의 모양까지 바꿉니다.

## threshold는 0.5로 되돌렸다

점수를 다시 찍었습니다. qwen 때 잰 13문장에 E2E·4주차·5주차 질문 10개를 더해 23문장입니다.
두 모델을 공정하게 비교하려고, 아래 표는 두 모델 모두 잰 공통 13문장만 top-1 점수로 셌습니다.

| 공통 13문장, top-1 기준 | qwen3-embedding | embeddinggemma |
| --- | --- | --- |
| 비 오는 날 늦게 오면 보상 받나요? | delay-compensation 0.456 | weather-delay 0.560 |
| 정책 질문 5개의 최저점 | 0.456 | 0.525 (쿠폰) |
| 정책이 아닌 질문 6개의 최고점 | 0.389 | 0.413 (인사) |
| 둘 사이 간격 | 0.067 | 0.112 |

gemma에서만 잰 10문장까지 넣으면 정책이 아닌 질문의 최고점은 0.447("2024-1234 주문한 가게 사장님 휴대폰 번호 ..." → refund-basic)까지 올라갑니다. 0.5는 이것까지 가르는 값이에요.

embeddinggemma는 전체적으로 점수를 높게 줍니다. 관련 있는 문서도, 관련 없는 문서도 올라갔어요.
그래도 두 그룹 사이 간격은 오히려 넓어져서(0.067 → 0.112) 0.5를 그 사이에 둘 수 있었습니다. qwen 때 0.42로 내렸던 걸 0.5로 되돌렸어요.

threshold가 임베딩 모델마다 다른 값이라는 걸 이번에 몸으로 봤습니다. 0.42든 0.5든 "좋은 임계값"이 아니라 "이 임베딩 모델, 이 문서 7건, 이 질문 몇십 개에서 두 그룹을 가르는 값"이에요.
그래서 `RagConfig` 주석에 두 모델의 값을 같이 적고, 임베딩을 바꾸면 다시 재야 한다고 남겼습니다.

잃은 것도 있습니다.

- 무관한 문서가 더 많이 붙습니다. "20분 늦었어요" 질문에 delay-compensation(0.73) 말고도 weather-delay(0.61), refund-after-delivered(0.58), refund-basic(0.54)가 topK 4를 꽉 채웠고, 환불 질문에는 cancel-policy(0.64), delay-compensation(0.55)까지 붙었습니다. 답은 맞았지만 프롬프트는 무거워졌어요.
- "라이더가 한참 안 와요"는 여전히 0.384로 못 잡습니다. "제 번호로 연락 주시게 해주세요"는 top-1부터 weather-delay로 틀렸어요(privacy 0.350).
- 키워드 대 임베딩 top-1은 9/10에서 8/10이 됐습니다. "태풍 때문에 늦는 것도 보상돼요?"가 weather-delay 대신 delay-compensation(0.482)을 골랐어요. 순위는 맞았지만 0.5 아래라 잘리는 경우도 둘(쿠폰 0.385, privacy 0.376) 있었습니다.

어느 임베딩이 더 낫다고는 말하지 않겠습니다. 질문 10개로 한 개 차이는 판단할 크기가 아니에요.

## E2E 15턴 — 달라진 것과 같은 것

같은 15턴 입력을 다시 보냈습니다. 15턴 모두 HTTP 200이었습니다.

달라진 턴은 두 개입니다.

- 4턴 "비 오는 날 늦게 오면 보상 받나요?"는 `ragDocs=[weather-delay(0.56), delay-compensation(0.55)]`로 두 문서가 붙었습니다. qwen 임베딩 + 0.42일 때와 같은 문서, 순서만 반대예요.
- 7턴 "방금 그 주문 취소 한 번 더 해주세요"가 처음으로 2024-1239를 골랐습니다. 응답은 "주문번호 2024-1239는 이미 취소된 상태입니다"였고, `cancelOrder` outcome 메트릭에 `ALREADY_CANCELED`가 1로 찍혔습니다. 멱등 분기가 모델 경로로 실행된 첫 장면입니다.

7턴이 나아진 게 임베딩 때문이라고는 보지 않습니다. 7턴의 RAG 문서는 cancel-policy 하나로 전과 같았고, 바뀐 건 모델이 고른 주문번호였어요.
한 번 돌린 결과라 확률적인 차이일 가능성이 더 커 보입니다. "7턴이 풀렸다"가 아니라 "7턴이 이번엔 맞았다"로만 적어 둡니다.

나머지 턴은 같은 컴포넌트가 같은 자리에서 움직였습니다. 3턴과 8턴은 Memory에서 주문번호를 꺼내 Tool을 불렀고, 11턴은 Input Guardrail이 8ms에 잘랐고, 13~15턴은 LLM 없이 handoff됐어요.

토큰 메트릭 수정도 실제 앱에서 확인했습니다. 태그 없는 `baedal.agent.tokens`가 44759로, prompt 39345 + completion 5414와 정확히 같았습니다.

## 4·5주차 실험 재측정

4주차 RAG 쪽 세 질문은 9번 모두 정책 수치를 담았습니다. 임베딩이 바뀌어도 이 결론은 같아요. RAG 없는 쪽은 임베딩을 쓰지 않아서 다시 돌리지 않았습니다.

5주차 반복 실험은 이랬습니다.

- 위치 질문 10번: Tool은 10번 모두 `getDeliveryStatus`, 시각은 10번 모두 "9월 25일 오전 5시 24분"으로 맞았습니다. `KoreanTime` 수정이 다른 실행에서도 버텼어요.
- "부근에 도착했습니다" 왜곡은 10번 중 2번 나왔습니다. 전 실행에서는 1번이었어요. 시각처럼 값으로 확정할 수 없는 표현이라 여전히 남은 위험입니다.
- 사장님 번호 요청 10번은 모두 거절했습니다.
- 번호 되읽기 3번 중 1번이 번호를 되읽었고, Output Guardrail이 `010-****-5432`로 바꿨습니다. 전 실행에서는 3번 중 2번이었어요.

## 남는 것

모델을 전부 Gemma로 맞추고 나서 보니, 채팅 모델 교체와 임베딩 모델 교체는 성격이 완전히 달랐습니다.

채팅 모델을 바꾸자 드러난 건 프롬프트 한 문장, 시각 해석 같은 "판단" 쪽 문제였어요. 코드는 한 줄도 안 바꿔도 돌아갔습니다.
임베딩 모델을 바꾸자 데이터 재적재가 필요했고, threshold라는 숫자 하나가 통째로 의미를 잃었습니다. 판단은 그대로인데 "무엇을 관련 있다고 볼지"의 눈금이 바뀐 거예요.

그래서 다음에 임베딩을 바꿀 일이 생기면, 설정보다 먼저 `scripts/scores.py`로 점수 분포부터 찍을 것 같습니다.
