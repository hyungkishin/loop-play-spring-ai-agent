# Round 6 — gemma4로 바꾸고 E2E를 다시 돌려 본 기록

Round 6 제출 문서(`00.운영가능한에이전트로묶기.md`)를 다시 읽어 보니, 10턴 표의 "컴포넌트 기여" 칸 중 몇 개는 로그가 아니라 추정이었습니다.

3턴은 "Memory가 세션을 이어받은 것으로 추정"이라고 적혀 있었고, 4턴의 "RAG Context가 붙은 LLM 호출"은 토큰 수가 커졌다는 것 말고는 근거가 없었습니다.
토큰이 커진 건 Memory가 쌓여서일 수도 있어서, 사실 RAG가 붙었는지 아닌지 가릴 수 없는 상태였어요.

그 상태에서 채팅 모델을 `qwen2.5`에서 `gemma4`로 바꾸게 됐습니다.
모델이 바뀌면 1~6주차에 쌓은 관찰이 그대로 유지되는지부터 다시 봐야 해서, 이번 기록은 "같은 체인, 다른 모델"로 E2E를 다시 돌린 결과입니다.

raw는 전부 `docs/6주차/실측-raw/` 아래에 있습니다.

- `gemma4-e2e-14턴-수정전.md`
- `gemma4-e2e-15턴-수정후.md`
- `gemma4-장애주입.md`
- `rag-threshold-점수분포.md`
- `scripts/` — 요청 스크립트, 로그 분리 스크립트, 점수 계산, Ollama 프록시

## 왜 gemma3가 아니라 gemma4인가

처음엔 "젬마"라고 하면 gemma3를 떠올렸는데, Ollama 라이브러리 페이지의 capability 표시를 보니 gemma3는 `vision`만 있고 `tools`가 없었습니다.
이 에이전트의 절반은 Tool Calling이라, tools가 없는 모델로 바꾸면 2주차 이후가 통째로 무너집니다.

`ollama show gemma4`로 받은 모델은 8.0B, Q4_K_M, context 131072, capability는 `completion / vision / audio / tools / thinking`이었습니다.
`application.yml`의 `spring.ai.ollama.chat.model`만 `gemma4`로 바꿨고, 임베딩은 `qwen3-embedding:0.6b` 그대로 뒀습니다.
임베딩까지 바꾸면 PgVector 차원(1024)과 적재된 벡터를 다시 만들어야 해서, 이번 비교에서 변수를 하나로 묶어 두고 싶었어요.

thinking 모델이라는 점이 걸렸는데, Spring AI 1.0의 `OllamaOptions`에는 think 옵션이 없고 응답 본문에 추론 과정이 섞여 나오지는 않았습니다.
다만 LLM 한 번 왕복이 6~21초로, qwen2.5 때(10턴 합계 42.9초 / 7회, 최대 10.1초)보다 확실히 느려졌습니다.
thinking 토큰이 `completionTokens`에 들어가서인지, 모델 크기 때문인지는 이번 기록으로 가르지 못했습니다.

## 턴마다 무엇이 기여했는지 로그로 남기기

추정을 로그로 바꾸려고 `TurnTraceAdvisor`(order=30)를 체인에 하나 넣었습니다.

```text
InputGuardrailAdvisor       order=5
MessageChatMemoryAdvisor    order=10
QuestionAnswerAdvisor       order=20
TurnTraceAdvisor            order=30   ← Round 6에 추가
OutputGuardrailAdvisor      order=50
PerformanceLoggingAdvisor   order=100
```

30에 둔 이유는 단순합니다.
Memory(10)와 RAG(20)가 요청을 이미 가공한 뒤라서, 이 자리에서는 prompt instructions에 과거 대화가 몇 개 끼어 있는지, context의 `qa_retrieved_documents`에 어떤 문서가 들어 있는지를 볼 수 있습니다.

```text
[Turn] conversationId=gemma-e2e-0925-v2 memoryMessages=6 ragDocs=[delay-compensation(0.46), weather-delay(0.43)]
```

Tool은 여기서 못 봅니다. Tool 실행은 ChatModel 호출 안쪽의 `DefaultToolCallingManager`에서 일어나서, Advisor 체인에서는 이미 끝난 뒤의 응답만 보이기 때문이에요.
그래서 Tool 기여는 기존 `[Tool] ...` 로그와 `Executing tool call` DEBUG 로그, `baedal.agent.tool.invoke` 메트릭으로 봤습니다.

로그를 턴별로 자르는 데서 한 번 헛발을 디뎠습니다.
요청 전후 로그 줄 수로 잘랐더니 `[Turn]`만 남고 `[Tool]`과 `LLM call`이 전부 빠졌어요. `bootRun` 출력이 늦게 flush돼서 두 턴 사이 경계에 떨어졌던 겁니다.
요청이 순차라서 턴마다 한 번씩만 찍히는 시작 마커(`[Turn]` / `[InputGuardrail]` / `[Handoff]`)로 다시 잘랐습니다.

## 수정 전 14턴 — 모델만 바꿨을 때

Round 6 10턴에 네 턴을 더 넣었습니다. 멱등 재취소(7턴), 지시어로 Tool 파라미터를 유추하는 턴(8턴), 법적 이슈 handoff(12턴)를 보고 싶었어요.

14턴 모두 HTTP 200이었고 스택트레이스는 없었습니다. 그런데 로그를 보니 세 턴이 걸렸습니다.

| 턴 | 입력 | 로그 | 응답 |
| --- | --- | --- | --- |
| 3 | 그 주문 지금 어디쯤이에요? | `memoryMessages=4 ragDocs=[]`, Tool 없음 | 주문번호를 다시 물음 |
| 4 | 비 오는 날 늦게 오면 보상 받나요? | `memoryMessages=6 ragDocs=[]` | "해당 내용은 확인이 필요합니다" |
| 7 | 방금 그 주문 취소 한 번 더 해주세요 | `ragDocs=[cancel-policy(0.50)]`, Tool 없음 | 2024-1234가 배달 중이라 취소 불가 |

3턴은 Round 6 문서의 "Memory가 이어받은 것으로 추정"이 뒤집힌 장면이라 오래 봤습니다.
`memoryMessages=4`니까 2턴의 "주문번호 2024-1234 어떻게 됐어요?"와 그 답은 프롬프트에 들어가 있었습니다. Memory는 제 할 일을 했어요.
그런데도 모델이 주문번호를 다시 물었습니다.

프롬프트를 다시 읽어 보니 원인 후보가 바로 보였습니다.

```text
- 주문번호가 발화에 없다면 임의로 주문번호를 만들어 Tool을 호출하지 않고,
  먼저 주문번호를 되묻습니다.
```

"발화에 없다면"을 gemma4는 "이번 사용자 메시지에 없다면"으로 읽은 것 같습니다.
qwen2.5는 같은 문장에서도 이전 대화를 이어받았으니, 이 문장은 원래부터 Memory와 충돌하고 있었는데 모델이 관대해서 안 보였던 걸로 보여요.
확정은 아닙니다. 같은 입력을 반복해서 비율을 재 보지는 않았습니다.

4턴은 원인이 모델 밖에 있었습니다. 질문을 직접 임베딩해서 문서별 점수를 찍어 봤더니 이랬어요. (`rag-threshold-점수분포.md`)

```text
비 오는 날 늦게 오면 보상 받나요?   delay-compensation 0.456 | weather-delay 0.426 | ...
비 오는 날 지연이면 보상 받나요?    delay-compensation 0.565 | weather-delay 0.511 | ...
```

Round 6 qwen 실행 때 문장은 "지연이면"이었고, 이번 문장은 "늦게 오면"이었습니다.
"지연"이라는 단어 하나가 빠지자 두 문서가 threshold 0.5 아래로 떨어져서 Context가 비었고, 모델은 프롬프트의 `[정책 인용 규칙]`대로 "확인이 필요합니다"라고 답했습니다.
모델은 오히려 규칙을 잘 지킨 거라, 이건 검색 단의 문제입니다.

## 두 군데 고친 것

프롬프트는 "이전 대화의 주문을 가리키면 가장 최근에 언급된 주문번호를 쓴다"와 "현재 발화와 이전 대화 어디에도 없을 때만 되묻는다"로 나눠 적었습니다.

threshold는 0.5에서 0.42로 내렸습니다.
근거는 점수 분포 하나입니다. 도메인 밖 질문(인사, "치킨 맛집 추천해줘", "오늘 날씨 어때요?")과 주문 상태 질문의 최고점이 0.389였고, 놓친 정책 질문은 0.426~0.456에 있었어요.
그 사이에 선을 그었는데, 표본이 20문장 남짓이고 간격이 0.04도 안 됩니다. 정책 문서가 늘거나 질문 표현이 바뀌면 다시 재야 하는 값이라고 `RagConfig` 주석에도 적어 뒀습니다.

threshold를 내린 대가도 바로 보였습니다. 4주차 재실행에서 "20분 늦었어요" 질문에 `delay-compensation(0.74), weather-delay(0.63), refund-basic(0.49), refund-after-delivered(0.48)` 네 건이 다 붙었습니다.
환불 문서 두 건은 이 질문과 상관이 없는데 프롬프트 토큰만 늘립니다. 모델이 답을 틀리지는 않았지만, "놓치는 것"과 "쓸데없이 붙는 것"을 맞바꾼 거라는 건 기억해 두려고 합니다.

같은 입력에 고객이 자기 번호를 말하는 턴(10턴)을 하나 끼웠습니다. Output Guardrail이 실제로 도는 장면을 보고 싶어서였어요.

주문번호는 Tool 로그에서 `2024-***`로 가려져 있어, 5·7턴이 2024-1234였다는 건 응답 본문과 `cancelOrder` outcome이 `NOT_CANCELABLE` 2회 / `CANCELED` 1회였다는 메트릭으로 맞춰 봤습니다.

3턴과 8턴이 이번 라운드에서 제일 보고 싶었던 장면이었어요.
8턴 입력에는 주문번호가 없습니다. "아까 처음 물어본 주문"이 2024-1234라는 건 Memory 14개 메시지 안에만 있고, 모델은 그걸 꺼내 `getOrderDetail`의 인자로 넣었습니다.
3주차 목표였던 "지시 대명사 해석 → Tool 파라미터 유추"를 한 세션 안에서 로그로 본 셈입니다.

4턴도 이제 "RAG가 붙었다"를 추정 없이 말할 수 있습니다. `ragDocs`에 두 문서가 찍혔고, 응답이 "비가 오는 날이라는 이유만으로는 어렵다", "실제 배달 지연 시간과 기상 특보 발효 여부를 기준으로" 같은 문서의 판단 기준을 가져다 썼어요.

## 고치지 못한 것

7턴은 여전히 틀렸습니다.
"방금 그 주문"은 6턴의 2024-1239를 가리키는데, 모델은 2024-1234를 골랐어요. 프롬프트의 "가장 최근에 언급된 주문번호"를 넣은 뒤에도 그랬습니다.
결과적으로 `ALREADY_CANCELED` 멱등 분기는 이번 E2E에서 LLM 경로로 한 번도 타지 않았습니다. 멱등성 자체는 `OrderToolsIdempotencyObservationTest`로 보장되지만, "모델이 재취소 요청을 멱등 분기로 보내는가"는 확인 못 한 채 남았습니다.

여기서 더 프롬프트를 깎을지 망설이다가 멈췄습니다.
대화 안에 주문이 둘 이상 나오면 "그 주문"은 모델에게 맡기기에 애매한 입력이라, 프롬프트보다는 되묻기(어느 주문인지 확인)나 세션 상태에 "최근 조작한 주문"을 따로 들고 있는 쪽이 맞아 보여요. 이건 다음 숙제로 넘깁니다.

9·10턴에서는 Output Guardrail이 한 번도 발동하지 않았습니다. 모델이 번호를 응답에 다시 쓰지 않았기 때문이에요.
10턴은 오히려 "라이더 연락처를 달라"로 잘못 읽고 거절했습니다. 안전하긴 한데 고객 요청(내 번호로 연락 달라)은 처리되지 않았습니다.

마스킹이 실제 요청에서 도는지는 따로 확인했습니다. "제 연락처 010-9876-5432 맞게 적으셨는지 그대로 다시 읽어 주세요"를 새 세션으로 세 번 보냈더니, 한 번은 거절했고 두 번은 번호를 되읽었습니다.
되읽은 두 번은 둘 다 `010-****-5432`로 나갔고, DEBUG 로그에 원본과 최종이 같이 남았습니다.

## 장애 주입 — 여기서 가장 크게 바뀐 것

Round 6 문서에서 "재현 명령만 준비했다"고 남겨 둔 두 장애를 이번에 실제로 돌렸습니다.

### PgVector DOWN

`docker stop baedal-pgvector` 후 두 질문을 보냈습니다.

```text
비 오는 날 늦게 오면 보상 받나요?          → Fallback 문구, HTTP 200, 30.09s
주문번호 2024-1234 지금 어디쯤이에요?      → Fallback 문구, HTTP 200, 30.07s
```

두 번째 결과를 보고 한참 멈췄습니다.
주문 위치 질문은 RAG가 필요 없는데도 실패했어요. `QuestionAnswerAdvisor`는 질문이 뭐든 먼저 벡터 검색을 하고, 검색에서 난 `CannotGetJdbcConnectionException`이 그대로 컨트롤러 catch까지 올라왔기 때문입니다.
게다가 Hikari 기본 `connection-timeout` 30초를 꽉 채우고 나서야 실패했습니다. 고객은 30초 동안 아무 응답 없이 기다리다가 "일시적인 오류"를 봅니다.

Round 6 문서에서 "RAG가 가장 취약해 보인다"고 썼던 게 추측이었는데, 실제로는 추측보다 나빴어요. RAG 저장소 하나가 죽으면 에이전트 전체가 죽는 구조였습니다.

### 고친 것

검색 실패를 "Context 없음"으로 내려앉히는 `FailSoftVectorStore`를 만들어 `QuestionAnswerAdvisor`에만 넣었습니다.
`similaritySearch`만 예외를 잡아 빈 리스트를 돌려주고, `baedal.agent.rag.failure`를 올리고, WARN 로그를 남깁니다.
`KnowledgeLoader`의 적재 경로에는 원본 VectorStore를 그대로 둬서 적재 실패는 조용히 묻히지 않게 했어요.
그리고 `spring.datasource.hikari.connection-timeout`을 2초로 줄였습니다.

같은 장애를 다시 넣었습니다.

```text
health                                   → DOWN (db DOWN), 2.01s
비 오는 날 늦게 오면 보상 받나요?          → "해당 내용은 확인이 필요합니다. 상담원 연결로 도와드리겠습니다." 12.5s
주문번호 2024-1234 지금 어디쯤이에요?      → getDeliveryStatus 호출, 정상 위치 응답 15.2s
```

로그에는 `[RAG] 검색 실패 — Context 없이 진행`이 턴마다 한 줄 찍히고, 이어서 `[Turn] ragDocs=[]`, 필요한 턴에는 `[Tool]`이 나옵니다.
정책 질문은 프롬프트의 모름 규칙으로 상담원 연결에 떨어지고, 주문 조회는 멀쩡히 돕니다. 이게 제가 원하던 degraded mode였어요.

남는 불편함도 있습니다. `FailSoftVectorStore`는 모든 `RuntimeException`을 삼킵니다. 쿼리 문법 오류 같은 버그도 "Context 없음"으로 보일 수 있어서, `rag.failure` 메트릭에 알람을 걸어 두지 않으면 조용한 품질 저하가 됩니다.

### Ollama DOWN

로컬 Ollama 서버는 이 머신의 다른 작업도 쓰고 있어서 프로세스를 죽이지 않았습니다.
대신 앱을 11435 포트로 붙이고, 11435→11434 TCP 포워더를 사이에 둔 다음 포워더를 끊었어요. 앱 입장에서는 채팅, 임베딩, 헬스체크가 전부 Connection refused가 납니다.

```text
health                                   → DOWN (ollama DOWN)
주문번호 2024-1234 지금 어디쯤이에요?      → Fallback 문구, HTTP 200, 0.01s
상담원 바꿔주세요                          → 상담원 연결 문구, HTTP 200, 0.002s
```

임베딩 실패는 `FailSoftVectorStore`가 받아 `[RAG] 검색 실패`로 넘기고, 그 뒤 채팅 호출에서 `LLM call failed ... ResourceAccessException`이 나서 컨트롤러 Fallback으로 떨어졌습니다.
Handoff는 LLM 호출 전에 끊으니 Ollama 없이도 정상이었어요. "정책적으로 정해진 흐름은 모델 전에 자른다"는 Round 5 결정이 장애 상황에서 한 번 더 값을 했습니다.

이번 재현은 "연결 거부"만 봤습니다. Ollama가 살아 있는데 응답이 느려지는 장애는 재현하지 않았고, 채팅 호출에 타임아웃을 따로 걸지도 않았습니다.
qwen 때보다 gemma4가 느린 걸 보면, 느린 장애 쪽이 실제로는 더 흔할 것 같아 마음에 걸립니다.

## 지표 하나가 두 배로 부풀어 있었다

E2E 뒤 메트릭을 보다가 `baedal.agent.tokens`가 65848인데 `type:total`은 32924인 걸 봤습니다. 정확히 두 배예요.
`PerformanceLoggingAdvisor`가 같은 카운터 이름에 prompt, completion, total 세 태그를 다 올리고 있어서, 태그 없이 조회하면 prompt + completion + (prompt + completion)이 됩니다.

Round 6 문서의 "10턴 뒤 `baedal.agent.tokens`가 39036까지 올라갔다"도 같은 방식으로 읽은 값이라, 실제 사용량은 그 절반 근처였을 가능성이 큽니다.
그 문서에는 정정 메모를 달았습니다.

total은 더 이상 기록하지 않고, 필요하면 `sum by(type)`으로 구하게 바꿨습니다. `AgentMetricsTest`에 "태그 없이 합쳐도 prompt + completion과 같다"는 검증을 넣었어요.

## E2E 표에는 안 보였던 오류 두 가지

턴 표만 보면 2턴은 "정상"인데, raw를 다시 읽다가 수정 전 2턴 응답의 "예상 도착 시각은 2026년 9월 25일 오후 3시 35분"에서 멈췄습니다.
그 실행은 새벽 3시 20분에 띄운 앱이었고, mock 주문의 예상 도착은 "지금 + 15분"이라 정답은 오전 3시 35분이었어요.
같은 입력을 10번 넣어 보니 7번이 오전을 오후로 바꿔 말했습니다. Tool이 `LocalDateTime`을 넘기고 해석을 모델에 맡긴 탓으로 보고, View가 "9월 25일 오전 4시 11분" 같은 문자열을 넘기게 바꿨더니 10번 모두 맞았습니다.
Guardrail로는 못 잡는 종류의 오류라, 5주차 보강 문서(`docs/5주차/06`)에 따로 적었습니다.

두 번째는 오류라기보다 제 설명이 틀린 것이었습니다.
`00` 문서에 "RAG는 Memory 다음이어야 '그 주문' 같은 지시어가 먼저 풀려 검색이 의미를 가진다"고 썼는데, `QuestionAnswerAdvisor`의 검색어는 이번 턴 사용자 문장뿐이었습니다.
5·6·7·10턴 문장을 따로 임베딩한 점수(0.515 / 0.519 / 0.504 / 0.456)가 E2E 로그의 `ragDocs` 점수(0.52 / 0.52 / 0.50 / 0.46)와 같았어요. Memory를 앞에 두는 근거는 4주차의 Memory 오염 하나만 남습니다. (`docs/4주차/06`)

## 남는 것

"LLM이 판단하고 시스템이 실행한다"는 1주차 문장이 이번 라운드에서 다르게 읽혔습니다.
모델을 바꿨을 때 흔들린 곳은 전부 "판단" 쪽이었어요. 지시어를 풀지 않거나(3턴), 틀린 주문을 고르거나(7턴), 요청을 잘못 읽었습니다(10턴).
"실행" 쪽인 Tool 결과 객체, Input Guardrail, Handoff, Fallback은 모델이 바뀌어도 로그 한 줄까지 똑같이 움직였습니다.

그래서 프롬프트 한 문장(3턴)과 threshold 하나(4턴)가 모델 교체만으로 드러났다는 게 제일 오래 남습니다.
qwen2.5에서는 통과하던 설정이었는데, 통과했던 이유가 설정이 맞아서가 아니라 모델이 관대해서였을 수 있다는 거죠.
프롬프트 수정이 개선인지 회귀인지 자동으로 재야 한다는 Round 6의 숙제가, 모델 교체까지 포함하는 숙제로 커졌습니다.
