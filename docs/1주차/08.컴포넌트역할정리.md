# 1주차 보강 — ChatClient, ChatModel, Advisor, Tool, VectorStore를 6주차 로그로 다시 설명하기

1주차 목표 중 하나가 "ChatClient, ChatModel, Advisor, Tool, VectorStore의 역할을 이해하고 설명한다"였는데, 1주차 문서에는 ChatModel이라는 단어가 한 번도 안 나옵니다.
그때는 ChatClient 한 줄로 첫 응답을 받는 데 집중했고, 나머지 넷은 이름만 알았어요.

6주차까지 와서 채팅 모델을 qwen2.5에서 gemma4로 바꾸고 E2E를 다시 돌렸더니, 다섯 개가 한 요청 안에서 어떤 순서로 움직이는지가 로그에 그대로 남았습니다.
그래서 이 문서는 1주차의 이해를 6주차 로그로 다시 설명하는 쪽으로 씁니다.

근거 로그는 `docs/6주차/실측-raw/gemma4-e2e-15턴-수정후.md`입니다.

## 한 요청이 지나가는 순서

E2E 5턴("그럼 그 주문 취소해주세요")의 로그입니다.

```text
03:26:33.501  [Turn] conversationId=gemma-e2e-0925-v2 memoryMessages=8 ragDocs=[cancel-policy(0.52)]
03:26:45.042  Executing tool call: cancelOrder
03:26:45.043  [Tool] cancelOrder(orderId=2024-***, reasonLength=5)
03:26:52.843  LLM call elapsedMs=19341 promptTokens=5091 completionTokens=711 totalTokens=5802
```

이 네 줄에 다섯 컴포넌트가 다 들어 있습니다.

## ChatClient — 요청을 조립하는 입구

컨트롤러가 직접 쓰는 건 ChatClient 하나입니다.

```java
chatClient.prompt()
        .user(req.message())
        .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, sessionId))
        .call()
        .content();
```

system prompt, Advisor 목록, Tool 목록은 생성자에서 `ChatClient.Builder`에 한 번 등록해 두고, 요청마다 바뀌는 사용자 문장과 세션 id만 넣습니다.
ChatClient는 이걸 `Prompt`로 조립해서 Advisor 체인에 흘려보내고, 끝에서 나온 응답을 `.content()`나 `.entity(...)`로 꺼내 줘요.
그러니까 ChatClient는 "무엇을 물을지"를 모으고 "받은 걸 어떤 모양으로 꺼낼지"를 정하는 자리이지, 모델과 직접 이야기하는 자리는 아닙니다.

## ChatModel — 모델과 실제로 이야기하는 자리

모델과 HTTP로 이야기하는 건 ChatModel이에요. 이 프로젝트에서는 Spring AI 스타터가 자동 구성한 `OllamaChatModel`이고, 코드에서 직접 부르는 곳은 없습니다.
`ChatClient.Builder`가 이미 이걸 품은 채로 주입되기 때문입니다.

이 경계가 실감난 건 모델을 바꿀 때였어요. qwen2.5에서 gemma4로 바꾸는 데 필요한 변경은 `application.yml`의 한 줄이었습니다.

```yaml
spring.ai.ollama.chat.model: gemma4
```

컨트롤러, Advisor, Tool 어디에도 모델 이름이 없습니다. 모델 종류는 ChatModel 뒤에 숨어 있고, 나머지는 ChatClient와 `Prompt` / `ChatResponse`라는 공통 타입으로만 이야기해요.

Ollama가 죽었을 때 터지는 곳도 여기입니다. 6주차 장애 주입에서 `LLM call failed ... I/O error on POST request for ".../api/chat"`이 났는데, `/api/chat`을 부르는 게 ChatModel이에요.

## Advisor — ChatModel 호출 앞뒤에 끼는 층

Advisor는 ChatClient와 ChatModel 사이에 층층이 끼어, 호출 전에 요청을 고치거나 호출 후에 응답을 고칩니다.
지금 `/api/v1/assistant`의 체인은 이렇습니다.

```text
InputGuardrail(5) → Memory(10) → RAG(20) → TurnTrace(30) → OutputGuardrail(50) → Performance(100) → ChatModel
```

1주차 06에서 "order가 낮을수록 바깥인지는 로그로 확인하지 않아서 단정하기 어렵다"고 적었는데, 이번 로그로 답이 나왔습니다.
마스킹이 걸린 요청의 로그 순서가 이랬어요.

```text
03:28:52.009  [Turn] conversationId=mask-probe-2-...        ← 30, 호출 전
03:28:55.797  LLM call elapsedMs=3788 ...                   ← 100, 호출 후
03:28:55.798  [OutputGuardrail] SENSITIVE_MASKED            ← 50, 호출 후
```

호출이 끝난 뒤에는 100이 먼저, 50이 나중에 찍혔습니다. 안쪽부터 풀려 나온다는 뜻이라, order가 낮을수록 바깥이 맞습니다.
Input Guardrail(5)이 injection을 막은 턴에서 `[Turn]`(30)이 아예 안 찍힌 것도 같은 얘기예요. 바깥에서 `chain.nextCall()`을 안 부르면 안쪽은 깨어나지도 않습니다.

## Tool — ChatModel 안에서 도는 실행

Tool은 Advisor가 아닙니다. 5턴 로그에서 `Executing tool call`과 `[Tool]`이 `LLM call` 로그보다 먼저, 그리고 `[Turn]`보다 나중에 찍혔어요.
Performance(100)가 재는 "LLM call 19341ms" 안에 Tool 실행이 들어 있다는 뜻입니다.

흐름은 이렇습니다. ChatModel이 모델에게 Tool 목록과 함께 질문을 보냅니다. 모델이 "cancelOrder를 이 인자로 불러 달라"고 답하면, ChatModel 안의 `DefaultToolCallingManager`가 우리 `OrderTools.cancelOrder`를 실행합니다. 그 결과를 붙여 모델을 한 번 더 부르고, 최종 문장을 받습니다.
2주차의 "LLM은 판단하고 실행은 Spring Bean이 한다"가 코드 경로로는 이렇게 생겼어요. 판단(어떤 Tool을 어떤 인자로)은 모델 응답에, 실행은 `@Tool` 메서드에 있습니다.

그래서 `baedal.agent.llm.latency`는 순수 모델 시간이 아니라 "모델 → Tool → 모델" 왕복 전체입니다. 6주차 대시보드에서 LLM 지연을 볼 때 Tool이 느려서인지 모델이 느려서인지 이 지표만으로는 못 가립니다.

## VectorStore — RAG Advisor가 쓰는 저장소

VectorStore는 정책 문서를 벡터로 저장하고 "이 질문과 가까운 문서"를 찾아 주는 저장소입니다. 이 프로젝트에서는 `PgVectorStore`이고, 직접 쓰는 곳은 두 군데예요.

- `KnowledgeLoader` — 앱이 뜰 때 문서를 임베딩해서 넣는다
- `QuestionAnswerAdvisor`(RAG, order=20) — 요청마다 사용자 문장으로 검색해서 결과를 프롬프트에 붙인다

5턴 로그의 `ragDocs=[cancel-policy(0.52)]`가 VectorStore 검색 결과입니다.
여기서 검색어는 이번 턴 사용자 문장 하나였습니다. Memory가 앞에서 넣은 과거 대화는 검색어에 안 들어가요. (자세한 확인은 `docs/4주차/06`)

VectorStore가 죽으면 RAG Advisor가 예외를 던져서 요청 전체가 실패했었는데, 6주차에 `FailSoftVectorStore`로 감싸 검색 실패를 "Context 없음"으로 바꿨습니다.

## 다섯 개를 한 문장씩

- ChatClient: 무엇을 물을지 모으고, 받은 걸 어떤 모양으로 꺼낼지 정한다.
- ChatModel: 특정 모델과 실제로 이야기한다. 모델을 바꿀 때 바뀌는 건 여기뿐이다.
- Advisor: ChatModel 호출 앞뒤에 끼어 요청과 응답을 고친다. order가 낮을수록 바깥이다.
- Tool: 모델이 고른 실행을 ChatModel 안에서 Spring Bean이 수행한다.
- VectorStore: 문서를 벡터로 저장하고, RAG Advisor가 요청마다 여기서 Context를 찾는다.

1주차에는 이 다섯 개를 "Spring AI 구성 요소 목록"으로 외웠다면, 지금은 로그 네 줄 안에서 각자 어디에 찍히는지로 기억하고 있습니다.
