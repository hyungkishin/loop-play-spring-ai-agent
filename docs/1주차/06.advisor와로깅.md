# 1주차 - Advisor 와 로깅

> 컨트롤러 끝에 `log.info()` 한 줄 박으면 되는 거 아닌가, 부터 시작했어요.

## 한 줄로 끝낼 수도 있는데 왜 Advisor 인가

처음엔 솔직히 좀 과해 보였어요.
응답 시간이랑 토큰 수 찍는 거면 `SupportController.triage()` 안에 `long start = ...` 적고 호출 끝나면 `log.info()` 한 줄 추가하면 됩니다.
근데 그건 한 컨트롤러에만 통하는 방식이고, 비슷한 컨트롤러가 늘어나면 같은 코드가 컨트롤러마다 복붙됩니다.

또 한 가지 — `SupportController` 는 `.call().entity(SupportResponse.class)` 인데, 만약에 측정 코드를 컨트롤러에 박으면 측정이 entity 변환 시간까지 포함하게 돼요.
순수 LLM 왕복만 보고 싶을 때는 그게 또 노이즈입니다.

`CallAdvisor` 는 `chain.nextCall(request)` 호출 직전/직후를 끼어들 수 있는 자리예요.
체인 자체가 ChatClient 의 호출 파이프라인이라, advisor 를 끼우면 "LLM 호출 그 한 번" 의 앞뒤를 잡을 수 있게 됩니다.
컨트롤러는 결국 그 advisor 가 끼인 ChatClient 를 쓸 뿐이고, 측정 로직은 따로 떼어진 컴포넌트로 존재해요.

이게 spring 의 다른 영역에서 본 AOP 와 결이 비슷하다 싶었습니다.
`@Around` 어드바이스로 메서드 호출 전후를 잡는 패턴인데, ChatClient 는 이걸 자기 도메인용 인터페이스 (`CallAdvisor.adviseCall`) 로 다시 만든 거 같아요.
이름이 그래서 같은 "Advisor" 인 것도 우연은 아닐 것 같고요.

## getOrder = 100 이 의미하는 거

스타터 코드 주석에 이미 "체인 바깥쪽에서 LLM 왕복 시간을 측정하기 위해 큰 값을 준다" 라고 적혀 있었어요.
처음 봤을 땐 "큰 값이면 바깥? 작은 값이면 바깥?" 이 헷갈렸습니다.

Spring 의 일반 `Ordered` 컨벤션은 작은 값이 먼저 실행되는 쪽이에요.
체인 형태로 advisor 가 끼어들 때 "먼저 실행되는 게 바깥" 이 일반적이긴 한데, 이 영역은 Spring AI 의 구현체에 따라 다를 수 있어서 단정하긴 좀 그렇습니다.
일단 starter 의 주석을 신뢰하는 쪽으로 두고, `getOrder() = 100` 으로 가져갔어요.
실제로 "바깥쪽" 인지 확인하려면 Advisor 두 개를 끼워서 실행 순서를 로그로 찍어보면 되는데, 거기까진 안 갔습니다.

## null 검사를 네 번 한 게 좀 답답하긴 합니다

Usage 메타데이터 꺼내는 코드가 이렇게 됐어요.

```java
ChatResponse chatResponse = response.chatResponse();
if (chatResponse != null) {
    ChatResponseMetadata metadata = chatResponse.getMetadata();
    if (metadata != null) {
        Usage usage = metadata.getUsage();
        if (usage != null) {
            promptTokens = usage.getPromptTokens();
            ...
```

`Optional` 로 감싸진 게 아니라 매 단계 nullable 이라, 매번 null 체크하는 게 좀 답답합니다.
스타터 주석에 "chatResponse() 또는 getMetadata() 가 null일 수 있으므로 방어적으로 확인할 것" 이라고 적힌 게 괜한 안내가 아니었어요.

이게 왜 null 일 수 있는지를 한 번 생각해봤는데, Ollama 처럼 토큰 수를 내려주지 않는 모델이 있거나, 토큰 수 집계가 비활성화된 옵션으로 호출됐을 때를 가정한 것 같아요.
정확한 경로는 Spring AI 코드를 안 까봐서 확신은 못 하겠고, 일단 null 이 정상 케이스에서도 떨어질 수 있다는 가정으로 방어 코드를 두었습니다.

토큰이 null 인 경우 로그에는 `promptTokens=null` 처럼 그대로 떨어지게 했어요.
0 으로 채우면 진짜 0 인 케이스와 구분이 안 되니까, null 그대로 흘리는 쪽이 솔직한 표현이라고 봤습니다.

## SupportController 에만 일단 등록한 이유

스타터 힌트가 "SupportController 에 `.defaultAdvisors(performanceAdvisor)` 로 등록" 만 적시한 게 의도라고 봐서 거기서 멈췄어요.
`PromptLabController` 에도 등록하면 정량 비교 결과랑 응답 시간/토큰을 같이 볼 수 있어서 자연스럽긴 한데, 한 단계에 너무 많은 변경을 묶는 게 부담스러웠어요.

`StreamingChatController` 는 더 까다롭습니다.
`CallAdvisor` 는 `.call()` 경로용이라 `.stream()` 경로는 안 잡혀요.
Spring AI 에 `StreamAdvisor` 가 별도로 있을 것 같은데, 이건 이번 미션 범위 밖이라 따로 안 건드렸습니다.
3단계 회고 끝에 적어둔 "TTFT 가 Advisor 레벨에서 잡히는지" 는 그래서 아직 못 푼 채로 남아요.

## 단위 테스트로 보장한 것

`PerformanceLoggingAdvisorTest` 에 다섯 케이스를 넣었어요.

1. `adviseCall_delegatesToChain_andReturnsDownstreamResponse` — `chain.nextCall(request)` 가 호출되고 그 반환이 그대로 다시 흘러나오는지 (advisor 가 응답을 가로채거나 변형하지 않는지)
2. `adviseCall_isNullSafe_whenChatResponseMissing` — `response.chatResponse()` 가 null 이어도 예외 없이 통과
3. `adviseCall_isNullSafe_whenMetadataMissing` — `chatResponse.getMetadata()` 가 null 인 경우
4. `adviseCall_isNullSafe_whenUsageMissing` — `metadata.getUsage()` 가 null 인 경우
5. `advisorMetadata_orderIsHighEnoughForOutermostMeasurement` — `getName()`, `getOrder()` 가 의도대로 박혀있는지

`SupportControllerTest` 두 케이스도 같이 손봤어요.
생성자가 `(builder, advisor)` 로 바뀌었으니까 mock 체인에 `builder.defaultAdvisors(advisor)` 호출이 추가됐고, 그게 한 번 정확히 advisor 와 함께 호출되는지 verify 를 추가했습니다.

`./gradlew test --rerun-tasks` 후 `build/test-results/test/` 디렉토리 안의 네 XML 파일을 보면:
- `TEST-com.baedal.support.PerformanceLoggingAdvisorTest.xml` 의 `<testsuite>` 가 `tests="5" skipped="0" failures="0" errors="0"`
- `TEST-com.baedal.support.SupportControllerTest.xml` 의 `<testsuite>` 가 `tests="2" failures="0" errors="0"` (advisor 주입 후 회귀 없음)
- `TEST-com.baedal.support.PromptLabControllerTest.xml` 의 `<testsuite>` 가 `tests="4" failures="0" errors="0"`
- `TEST-com.baedal.support.StreamingChatControllerTest.xml` 의 `<testsuite>` 가 `tests="2" failures="0" errors="0"`

총 13 케이스가 같은 실행 batch 에서 통과했습니다.

## 단위 테스트로 못 보는 것

가장 거슬리는 게 "log.info() 가 진짜 의도된 메시지로 떨어지는가" 입니다.
지금 테스트는 advisor 가 응답을 가로채지 않고 chain 으로 흐름이 지나가는지까지만 보장하지, 로그 라인 자체는 확인 안 했어요.
Logback 에 capture appender 를 끼워서 잡을 수도 있는데, 그건 다음 단계로 미뤘습니다.

또 한 가지 — 실제 토큰 수가 진짜 모델이 사용한 수와 같은지는 단위 테스트로 검증이 안 돼요.
mock 으로 42, 17, 59 를 주입했는데 실제 Ollama 응답에선 이게 어떻게 들어오는지, 또는 안 들어올 수도 있는지는 직접 호출해본 다음에 알 영역이에요.
회고 윗부분에서 "Ollama 가 토큰 수를 안 내려줄 수도 있다" 라고 추측만 적었는데, 이건 실제로 한 번 호출해봐야 확정됩니다.

## 안 풀린 채로 두는 것들

스트리밍 응답의 TTFT 측정이 여전히 미해결이에요.
3단계 끝에서도 적었고 이번 4단계 끝에서도 다시 적게 되네요.
`CallAdvisor` 와 `StreamAdvisor` 가 별개라면, advisor 두 개를 별도 클래스로 만들거나 하나로 합치는 방법이 있을 텐데, 이건 1주차 범위 밖이라 다음 주차 영역으로 미뤘습니다.

Advisor 등록을 `PromptLabController` 까지 확장하는 것도 미해결로 남겼어요.
정량 비교가 본 의미를 가지려면 "프롬프트 A 가 더 적은 토큰으로 더 안정적인 분류를 한다" 같은 비교가 가능해야 하는데, 그러려면 PromptLab 호출도 같은 advisor 를 타야 합니다.
이건 사실 추가 코드 한 줄이긴 한데, 회고 흐름상 4단계의 "Advisor 패턴 도입" 자체를 깔끔하게 한 단계로 끊고 싶어서 일부러 미뤘어요.
다음 손볼 때 같이 가져갈 영역으로 적어둡니다.
