# 2주차 - Observability 와 AI 코드 리뷰 (단계 4)

> "Tool 호출이 들어왔을 때 LLM 과 서버가 정확히 몇 번 오가는가", 1주차에 깔아둔 advisor 한 줄로 이걸 다 볼 수 있을 줄 알았는데, 막상 보니 advisor 가 잡는 시점이 한 곳이라 좀 까다로웠어요.

## ChatController 에도 advisor 를 같이 붙인 이유

이 단계 들어가서 처음 시도한 게 `"안녕하세요"` 를 `/api/v1/chat` (round 1 baseline) 과 `/api/v1/assistant` (round 2) 에 같이 보내서 토큰 차이를 비교하는 거였어요.
그런데 ChatController 쪽 advisor 로그가 한 줄도 안 떨어졌습니다.

확인해보니 ChatController 가 `chatClientBuilder.build()` 를 매 요청마다 호출하면서 `defaultAdvisors(...)` 가 빠져 있었어요. 1주차에 SupportController 에만 advisor 를 등록하고 ChatController / PromptLab / Stream 은 다음 단계로 미뤘던 게 여기서 다시 발목을 잡았습니다.

선택지가 두 개였어요.
- (A) Round 1 baseline 비교는 포기하고 round 2 만 측정
- (B) ChatController 에 advisor 한 줄 추가하고 round 1 vs round 2 같은 그릇으로 측정

(A) 가 회고체 흐름상 깔끔할 수도 있는데, 그러면 "Round 1 vs Round 2 입력 토큰" 비교가 빈 자리로 남게 됩니다. 그래서 (B) 로 가서 ChatController 도 advisor 가 붙는 ChatClient 를 들고 있게 바꿨어요.

```java
public ChatController(ChatClient.Builder builder, PerformanceLoggingAdvisor advisor) {
    this.chatClient = builder.defaultAdvisors(advisor).build();
}
```

생성자에서 한 번만 build 하니까 1주차 SupportController 와 같은 패턴이 됐고, advisor 가 매 요청마다 발화하기 시작했습니다.

## Round 1 vs Round 2: 4셀 비교

같은 발화를 두 엔드포인트에 보내고 advisor 가 잡은 promptTokens 를 모았어요.

| 발화 | round 1 `/api/v1/chat` (system prompt 없음, tools 없음) | round 2 `/api/v1/assistant` (system prompt + tools 3개) |
|---|---|---|
| "안녕하세요" | promptTokens=32 | promptTokens=1329 |
| "주문번호 2024-1234 배달 어디쯤?" | promptTokens=50 (Tool 호출 없음) | promptTokens=2803 (Tool 호출 후 2차 round) |

raw 로그는 `실측-raw/단계4-4셀비교.txt`.

이 표에서 손에 잡힌 게 세 가지.

(1) "안녕하세요" 만으로도 1297 토큰 차이, 사용자 입력은 한국어 4 토큰 정도일 텐데, round 2 가 1297 토큰을 더 먹습니다.
이 1297 의 정체는 (a) `AssistantPrompt.SYSTEM_PROMPT` 본문 + (b) Tool 3개의 description + JSON schema 두 가지예요.
1주차에 SYSTEM_PROMPT 가 ~1130 토큰을 먹는다고 적었던 것과 비교하면, 2주차에 추가된 게 ~170 토큰 정도. 그게 Tool 3개의 description + 파라미터 schema 입니다.
Tool 하나 추가될 때마다 약 50~60 토큰 씩 매 호출 비용이 늘어난다 는 게 한 줄로 잡혀요. 운영 환경에 Tool 20개를 박으면 호출당 1000~1200 토큰을 description 으로만 먹습니다.

(2) "주문번호..." 발화에서 50 vs 2803, 56배 차이, 같은 한 문장이 round 1 은 50 토큰으로 끝나는데 round 2 는 2803.
2803 의 정체는 (a) 시스템 + Tool description (1329 정도) + (b) 1차 LLM 응답 (Tool 호출 의도) + (c) Tool 결과 JSON (`{"orderId":"2024-1234","status":"DELIVERING","riderLocation":"역삼역 사거리 부근",...}`) + (d) 사용자 발화 가 모두 합쳐진 거예요.
2차 round LLM 입장에선 1차 round 의 모든 컨텍스트 + Tool 결과를 다시 입력으로 받아서 자연어로 변환해야 하니까, 이게 비용이 커요.

(3) round 1 baseline 응답이 거의 거짓말, 같은 "주문번호 2024-1234 배달 어디쯤?" 에 대해 round 1 chat 은 "주문 정보를 확인할 수 있는 데이터가 없네요. 배달사와 연락하거나..." 라고 답했어요.
Tool 이 없으니까 모르는 게 맞는데, "배달사와 연락하라" 는 안내가 잘못된 자기 추론이에요. 우리 플랫폼이 곧 배달사입니다.
round 2 는 같은 질문에 "역삼역 사거리 부근에서 배송 중입니다" 라고 정확히 답했고요.
Tool 없는 LLM 은 그럴듯한 거짓말을 한다, Tool 있는 LLM 은 정확한 답을 한다, 이 한 줄이 사실 round 2 의 가치 명제 전부예요.

## Tool 왕복 4지점: 한 호출 안에서 일어나는 일

`/api/v1/assistant` 에 "주문번호 2024-1234 배달 어디쯤에 있어요?" 한 줄을 보냈을 때 콘솔에 박힌 4 지점 로그.
raw 는 `실측-raw/단계4-Tool왕복.txt` 에 그대로 있어요.

```text
T0  16:05:36.847  DEBUG  DefaultToolCallingManager  Executing tool call: getDeliveryStatus
T1  16:05:36.848  DEBUG  MethodToolCallback         Starting execution of tool: getDeliveryStatus
T2  16:05:36.849  INFO   OrderTools                 [Tool] getDeliveryStatus(orderId=2024-1234)
T3  16:05:36.849  DEBUG  MethodToolCallback         Successful execution of tool: getDeliveryStatus
T4  16:05:36.849  DEBUG  DefaultToolCallResultConverter  Converting tool result to JSON.
T5  16:05:38.355  INFO   PerformanceLoggingAdvisor  LLM call elapsedMs=5844 promptTokens=2803 ...
```

T0 ~ T4 가 Tool 실행 구간, T5 가 2차 LLM 응답 완료.
T0~T4 사이 elapsed 가 2ms 정도예요, Tool 실행 자체는 빠르고, 시간은 거의 다 LLM 호출에 박혀 있어요 (5844ms).

advisor 가 어디서 끼어드는가 는 5844ms 라는 숫자 한 곳에서 다 잡힙니다.
1차 LLM 호출 (Tool 호출 의도 결정) 시작, Tool 실행, 2차 LLM 호출 (Tool 결과, 자연어) 완료까지를 advisor 가 한 번에 감싸고 있어요.
1주차 회고 06 의 `getOrder() = 100` 이 "체인 바깥쪽에서 LLM 왕복 시간을 측정한다" 였는데, 그 "왕복" 이 round 2 에선 실제로 두 번의 LLM 호출 + Tool 실행을 다 포함한 왕복이 된 거예요.

한 가지 발견, advisor 의 `LLM call elapsedMs=5844 promptTokens=2803` 한 줄은 사실 마지막 LLM 호출의 토큰 입니다. 1차 LLM 호출의 promptTokens (~1349) 는 advisor 가 잡지 않아요. 단계 1 콘솔 로그를 봐도 Tool 호출이 일어난 시나리오 1, 2 가 promptTokens=2801, 2887 한 줄만 잡혔습니다.
이게 진짜 운영 비용을 다 잡으려면 advisor 가 chain 의 각 LLM 호출마다 발화해야 하는데, 지금은 마지막 응답만 잡고 있어요.
1주차 06 회고 끝에 적어둔 "StreamAdvisor 는 다음 단계 영역" 의 변형판이 여기 다시 등장합니다, chain 의 중간 호출도 같이 잡으려면 advisor 위치를 다시 봐야 해요. 이건 3주차 ChatMemory 와 함께 다시 두드릴 영역으로 미뤘습니다.

## AI 가 만든 cancel Tool 코드를 보고 결함 3개를 골랐어요

ChatGPT 에 다음 한 줄 프롬프트로 코드를 받았어요 (실제 ChatGPT 호출 대신, 실무에서 자주 보던 패턴을 그대로 재구성).

> "Spring AI 1.0으로 배달 주문 취소 Tool을 만들어줘. `@Tool` 어노테이션을 써야 해."

받은 코드 (원본):

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class OrderCancelTool {

    private final OrderRepository orderRepository;

    @Tool(description = "Cancel an order by ID")
    public Order cancelOrder(String orderId) {
        Order order = orderRepository.findById(orderId)
                .orElseThrow(() -> new EntityNotFoundException("Order not found: " + orderId));

        order.setStatus(OrderStatus.CANCELED);
        return orderRepository.save(order);
    }
}
```

언뜻 보면 깔끔합니다. JPA 패턴이고, `@Tool` 만 빼면 회사 코드에서 자주 보는 형태예요.
이번 라운드를 두드리고 나서 이 코드를 다시 보니까 세 곳이 즉시 빨갛게 보였습니다.

### 결함 1: 멱등성 분기가 없다

같은 `orderId` 로 두 번 호출되면 두 번째 호출도 그대로 `setStatus(CANCELED) + save(...)` 가 실행됩니다.
이미 CANCELED 인 주문도 다시 CANCELED 로 덮어쓰는 거예요.

단계 2 의 케이스 B 와 정확히 같은 시나리오가 만들어집니다:
- `canceledAt` (만약 추가됐다면) 이 덮어씌워져서 환불 SLA 가 흔들림
- LLM 이 "취소되었습니다" 를 두 번 사용자에게 전달
- 결제 PG 환불 API 가 코드 뒤에 붙어 있다면 이중 환불 시도

개선: `CancelOrderResult` + `Outcome.ALREADY_CANCELED`

```java
@Tool(description = """
        주어진 주문번호의 주문을 취소한다.
        ...
        이미 취소된 주문을 다시 취소 요청해도 ALREADY_CANCELED를 반환한다 (멱등).
        ...
        """)
public CancelOrderResult cancelOrder(String orderId, String reason) {
    Order order = orderRepository.findById(orderId).orElse(null);
    if (order == null) {
        return new CancelOrderResult(orderId, Outcome.NOT_FOUND, "...");
    }
    if (order.status() == OrderStatus.CANCELED) {
        return new CancelOrderResult(orderId, Outcome.ALREADY_CANCELED, "...");
    }
    if (!order.isCancelable()) {
        return new CancelOrderResult(orderId, Outcome.NOT_CANCELABLE, "...");
    }
    order.cancel(reason, LocalDateTime.now());
    return new CancelOrderResult(orderId, Outcome.CANCELED, "...");
}
```

### 결함 2: 예외를 그대로 throw 한다

`EntityNotFoundException` 이 호출 스택을 통과해 Spring AI 로 떨어집니다.
Spring AI 가 그걸 어떻게 처리하는지가 모델 / 버전 / 설정에 따라 갈리는데, 두 가지 케이스가 가능해요.
- 호출자에게 500 으로 그대로 떨어짐, LLM 이 응답을 못 만들고 사용자에겐 "오류가 발생했습니다"
- LLM 에게 `tool returned error: ...` 로 전달됨, LLM 이 paraphrase 해서 "주문을 찾을 수 없습니다" 비슷한 응답을 만들 수도 있지만 일관성이 없음

LLM 에이전트에서 예외는 데이터의 한 형태로 변환하는 게 안전 합니다.
존재하지 않는 주문은 `NOT_FOUND` outcome 으로 돌려주고, 그 message 를 LLM 이 사용자에게 어떻게 전달할지 선택할 수 있게 해야 해요.

개선: outcome enum 으로 변환 (결함 1 의 개선 코드에 이미 포함)

### 결함 3: 내부 엔티티 `Order` 를 그대로 반환

`return orderRepository.save(order);` 한 줄이 가장 무서워요.
이 `Order` 가 JPA entity 면, `@OneToMany` lazy 컬렉션이 JSON 직렬화 시점에 줄줄이 따라옵니다.
LLM 입력 토큰이 미친 듯이 늘어나고, 더 큰 문제는 노출되면 안 되는 필드 들이 같이 노출된다는 거예요.
- 라이더 전화번호, 매장 사장님 연락처
- 결제 PG transaction id (PG 사 내부 식별자)
- 배달 주소 상세
- 회원 ID, 회원 등급, 회원 마케팅 동의 여부

이 중 하나라도 LLM 입력에 들어가면, LLM 이 그걸 응답으로 새어 내보낼 가능성이 항상 있습니다.
"단지 description 에 'don't expose phone number' 라고 적으면 된다" 는 가드레일은 단계 3 실험에서 봤듯이 키워드 매칭에만 의존하기 때문에 항상 통하지 않아요.

개선: View DTO 로 변환, 이건 우리가 이미 단계 1 에서 `OrderDetailView`, `DeliveryStatusView`, `CancelOrderResult` 로 분리했어요.
View DTO 가 곧 Tool ↔ LLM 경계의 화이트리스트 입니다.

### 결함 4: description 이 빈약

`"Cancel an order by ID"` 한 줄로는 단계 3 의 버전 B 와 같습니다.
LLM 이 언제 호출해야 할지, 실패 시 무엇이 반환되는지 모르는 채로 호출 결정을 내려요.

이건 위 세 결함보다 작은 영향이긴 한데, 단계 3 정량 비교에서 description 한 줄 차이가 호출률 ±1/5 를 만들었던 걸 보면 그 자체로도 무시 못 할 결함입니다.

### 결함 5: 권한 검증 없음 (운영 환경에서)

지금 우리 Mock 도 마찬가지긴 한데, AI 가 생성한 코드는 `orderId` 만 받아서 그 주문이 호출자의 것인지를 안 봅니다.
실제 배달 시스템이라면 `cancelOrder("2024-1234", ...)` 가 호출됐을 때 그 호출이 진짜 그 주문 고객의 권한으로 왔는지를 확인해야 해요. 안 그러면 다른 사람의 주문을 취소할 수 있게 됩니다.

이건 Spring Security 영역이라 회고 범위 밖이긴 하지만, 결함 목록에는 같이 박아두는 게 솔직합니다.

세 개 골라야 했다면 1, 2, 3 입니다. 4, 5 는 important 하지만 데이터 손상 / 정보 노출 보다는 한 단계 덜 critical 한 위치예요.

## advisor 가 PromptLab 까지 안 붙은 것

1주차 06 회고에서 미뤘던 게 단계 4 들어와서 또 한 번 손을 댔어요.
ChatController 까지는 advisor 를 붙였는데, PromptLabController / StreamingChatController 는 여전히 advisor 없이 돌고 있어요.

PromptLabController 는 호출별로 `system(req.systemPrompt())` 가 다르기 때문에 1주차에 `.defaultSystem` 으로 잠그지 않고 호출별로 system 을 적용하는 패턴이에요. 이 경우 `defaultAdvisors(advisor)` 를 적용하면 advisor 는 호출별 다른 system 과 함께 잘 돌아갑니다. 그래서 한 줄 추가로 가능한 영역인데, 회고 분량이 너무 늘어나서 일부러 미뤘어요.

StreamingChatController 는 `CallAdvisor` 로는 못 잡고 `StreamAdvisor` 가 필요한 경로라, 별도 advisor 가 필요합니다. 이건 3주차 또는 4주차 영역.

## 안 풀린 채로 두는 것들

1차 LLM 호출의 promptTokens 가 advisor 에 잡히지 않는다.
Tool 호출이 일어나면 advisor 가 보는 응답은 chain 의 최종 응답이라, 중간 LLM 호출은 토큰이 안 잡혀요.
단계 4 4셀 표의 round 2 "주문번호..." 셀이 `promptTokens=2803` 인데, 이건 2차 round 이고 1차 round 의 ~1349 는 그래프에서 빠져 있습니다.
운영 비용 측정으로 가져가려면 chain 의 각 LLM 호출마다 advisor 가 한 번씩 발화해야 하는데, 이건 Spring AI 의 advisor chain 구조를 더 까봐야 할 영역이에요.

Tool 실행 자체의 elapsed 측정도 별도 advisor 가 필요.
T0~T4 사이 2ms 라는 게 지금은 콘솔에서 timestamp 빼서 손으로 계산해야 잡혀요.
Tool 실행 단위로 latency 가 잡히는 advisor 가 따로 있어야 하는데, 이건 Spring AI 1.0 에 ToolCallback 인터페이스가 있어 wrap 으로 만들 수 있을 것 같긴 한데 회고 범위에선 안 했습니다.

AI 코드 리뷰는 한 번만 두드렸어요.
같은 프롬프트로 GPT-4, Claude, Gemini 에 각각 한 번씩 두드려보고 결함 분포가 어떻게 다른지 비교하면 모델별 "안전한 default" 를 잡을 수 있을 텐데, 그건 시간 부담이 있어 미뤘습니다.
